## Understanding Table Description Files in Catalog

Each table in `catalog/` has a `.md` file with the following sections:

### Status
- **frequentType** — table type: `block` or `minute/hour/day`.
- For `block` tables: tracked by **block number**, `fromBlock`/`toBlock` columns indicate the processed block range.
- For `minute/hour/day` tables: tracked by **time**, `fromEpochSecond`/`toEpochSecond` columns indicate the processed time range (epoch seconds).
- Record count / file count / size: describe current size (helps assess cost when modifying old tables).

### Lineage
- **Upstream tables** = list of input tables this table depends on (corresponds to `list_input_tables` in SQL header).
- **Downstream tables** = list of other tables that use this table as input.
- Origin tables (`<chain>_origin.*`) are sourced from RPC, **no upstream**.
- Upstream meaning: the job only processes the **intersection** of upstream ranges, expanded relative to the current output range.

### Schema
- Column list with data types (`string`, `bigint`, `int`, `double`, `decimal`, `date`, `timestamp`), **Index** columns (sequential index number, typically `block_date, block_number, block_time`), **Partition** column (`x` = partition column), and example values.
- `number_index_columns` in SQL header = number of leading index columns in Schema.

### SQL Transform
- **Header**: key=value job configurations. Important keys:
  - `frequent_type`: block or time.
  - `list_input_tables`: upstream list (corresponds to Lineage section).
  - `output_table`: single output table of the job (principle: 1 Job = 1 Table).
  - `partition_by`: partition column.
  - `write_mode`: `Append` or `Overwrite`.
  - `pre_decode_tables` (decode job): list of event names (comma-separated without spaces) that the decode engine writes results to **temp tables** before the SQL body runs; SQL body reads from these temp tables. Output is `<chain>_decoded.*` table. Columns retain **camelCase** per ABI parameter names.
  - `register_evm_call` (contract metadata job): registers ABI list (comma-separated without spaces) for SQL to call **view functions** (name, symbol, decimals...) via RPC. SQL call syntax: `<abi_name>(CONCAT(contract_address, ' function_name'))` — exactly **1 space** between address and function name; functions with parameters append after function name, separated by spaces. Function returns string, cast when other type needed. Combined with `${if table_existed}` + index column for **deduplication** — only calls for new contracts not yet in output. Output is `<chain>_contract.*` table.
- **SQL Body**: data transformation logic. Dynamic variables `${from}`/`${to}` are auto-calculated by the system per properties, no manual setting needed. Variable `${table_name}` and other `<table_name>` variables (defined in header) reference input tables.

### ABI
- If the table has decode (`pre_decode_tables`) or calls view functions (`register_evm_call`), the file lists events/functions in the ABI: each event shows signature (`EventName(indexed type param, ...)`) with JSON block; each view function shows `name(params) returns (type)`.
- Decoded table columns correspond to event parameter names in the ABI.

## Design File Format — MUST Match Catalog Table Info Files

Design files in `docs/<problem-name>/design/` must follow the **exact same format as table info files in `catalog/`** — same section structure, headings, tables, code blocks as files generated by `build_catalog.py` (e.g., `catalog/ethereum.blocks.md`). Specifically:

1. **Heading**: `# <schema>.<table_name>` (full table name, no backticks).
2. **`## Status`**: table `| Property | Value |` with rows: Creation Date, Last Update Date, Record Count, File Count, Size, frequentType, fromBlock, toBlock, fromEpochSecond, toEpochSecond. For new design tables: use `N/A` for unknown values, `frequentType` is required.
3. **`## Lineage`**: bullets `- **Upstream tables**: <table1>, <table2>` and `- **Downstream tables**: <table1>, <table2>`; RPC source tables write `_RPC Node (Blockchain)_`, no downstream write `_None_`.
4. **`## Schema`**: table `| Column | Type | Index | Partition | Example |` — Index column numbered sequentially starting from 1, Partition column marked `x`, Example is illustrative value in `` `value` `` format.
5. **`## SQL Transform`**: consists of `### Header` (table `| Key | Value |` listing job configuration key=value) and `### SQL Body` (SQL code in ```sql ... ``` block).
6. **`## ABI`** (only when `pre_decode_tables` or `register_evm_call` exists): each group under `### <abi_name>`, each event/function under `#### <signature> — event` (or `— function`), with JSON block.

Refer to `template/table_catalog.md` and compare with existing files in `catalog/` to ensure correct format.

## Responsibilities

1. Read `docs/<problem-name>/Data_Requirement.md` to understand requirements — which data tables the problem needs.
2. Run `python script/build_catalog.py` to **get the latest information** of all tables in the data warehouse (schema, status, lineage, record count, size). Script regenerates the `catalog/` directory — this reflects the current warehouse state, do NOT rely on potentially outdated old catalogs.
3. Read `catalog/lineage.md` (just built in step 2) to understand existing tables and dependencies; only deep-dive into files directly relevant to the problem (upstream/downstream), do NOT read the entire catalog.
4. Compare existing tables with Data_Requirement → identify which tables are sufficient, which are **missing** and need to be created/modified.
5. For each missing/needs-design table:
   - New table → create file in `docs/<problem-name>/design/` following the **"Design File Format"** above — i.e., same format as table info files in `catalog/`.
   - Existing table needing modification → copy file from `catalog/` to `docs/<problem-name>/design/`, edit on the copy, **preserve format**.
6. Each design file must be complete, in correct order and format like catalog files: `# <schema>.<table_name>` → `## Status` → `## Lineage` → `## Schema` → `## SQL Transform` (Header + SQL Body) → `## ABI` (if applicable).
7. If existing tables are sufficient → return "Current tables are sufficient", do NOT create files.
8. After completing design (≥ 1 design file) → run `python script/build_lineage_from_design.py <problem-name>` to generate `docs/<problem-name>/design/lineage.md`. Check dependency graph and status of each table (✅ EXISTS / 🔄 DEV / ❌ NEEDS CREATION); if the script warns about inconsistencies between declared downstream and actual graph, review design before handover.

## Design Principles

1. **System stability is priority #1**: Minimize changes to running tables. If a table is too large (high rerun cost) → prefer creating new tables rather than modifying existing ones.
2. **Reuse**: New tables should be usable across multiple problems.
3. **Follow conventions**: Table names, columns, partitions follow naming conventions: `<chain>_origin`, `<chain>`, `<chain>_decoded`, `<chain>_contract`, `<chain>_token`.
4. **Follow format**: SQL header (key=value) + `===` + body, variables `${chain_name}`, `${from}`, `${to}`, `${table_name}`.
